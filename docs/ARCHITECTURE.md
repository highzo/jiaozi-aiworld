## 为什么用浏览器做渲染层

三种目标设备（x86 电脑、安卓手机、ARM 开发板）唯一的公共 UI 运行时就是浏览器内核。

| 方案 | 电脑 | 安卓 | 开发板 | 手机远程接入 |
|---|---|---|---|---|
| X11 + 原生 Qt/GTK | 好 | 需 proot + X server，脆弱 | 需驱动/合成器，分辨率一变就崩 | 要 VNC，体验差 |
| Wayland 合成器自研 | 好 | 基本不可行 | 需要 GPU 支持 | 要额外串流 |
| **浏览器渲染 + 本地服务** | 好 | 原生 | Chromium 已有现成支持 | 天然支持，同一 URL |

代价说清楚：拿不到原生 GPU 加速的窗口合成，跑不了 X11 应用。换来的是"一套 UI 三端一致"。

## 数据流

### 请求（人 → 系统）

前端 `JZ.api.get/post` → `/api/*` → 具体模块 → JSON。
所有写操作成功后向 EventBus 发一个事件，例如 `fs_change`。

### 事件（系统 → 所有客户端）

```
GET /api/events          一次长连接，所有客户端订阅同一总线
  data: {"t":"term","id":"ab12","d":"bash-5.3$ "}
  data: {"t":"fs_change","d":{"path":"/home/pi/a.txt","action":"write"}}
  data: {"t":"notify","d":{"title":"...","body":"..."}}
  data: {"t":"ui","d":{"action":"open","app":"files","path":"/home/pi"}}
```

用 **chunked transfer** 而不是 `Content-Length`，因为 SSE 是无限流。
`?ms=1500` 可以让流在 1.5 秒后自行结束（截图 / 一次性抓取 / 调试用）。

每个客户端一个 `queue.Queue(maxsize=2000)`。慢客户端丢最旧的事件，**绝不阻塞内核**——
开发板上一个卡住的浏览器标签不能拖垮整个服务。

### 多客户端 = 同一个桌面

窗口是每个客户端自己的（各自的 DOM），但**状态是共享的**：

- 文件系统共享（本来就是同一份）
- AI 会话共享（`sid` 相同的上下文）
- 剪贴板、通知、壁纸共享
- AI 的 `ui_open` 广播给所有客户端 → 每台设备上都会弹出那个窗口

这是"人和 AI 共用一张桌子"在工程上的落地方式：不是让 AI 模拟点击，
而是让 AI 调用和 UI 完全相同的接口，再由事件总线把结果铺到每一块屏幕上。

## Agent 循环

```
用户输入
   │
   ├─ 追加 user 消息
   ├─ 组装 messages（system + 最近 N 条，工具结果超长截断）
   │
   ▼
┌──► LLMClient.chat(stream=True)
│      │  delta.content → 事件流（前端逐字显示）
│      │  增量拼装 delta.tool_calls
│      ▼
│   有 tool_calls ?
│      │ 否 → 结束，返回最终文本
│      │ 是
│      ▼
│   对每个 call：
│      ├─ 工具名不存在 → 回填错误文本
│      ├─ 需要审批？ ── 是 → 发 approval 事件 → 阻塞等人（默认 300s 超时=拒绝）
│      ├─ tools.dispatch()  → 真实执行（和 UI 同一套函数）
│      └─ 结果回填：原生协议用 role=tool；提示协议用 role=user 的【工具结果】
│
└── 步数 +1，未超过 max_steps 就继续
```

### 双协议

| | 原生 function calling | 提示协议 |
|---|---|---|
| 触发 | `native_tools: true` | `false`，或模型报错自动降级 |
| 模型要求 | 支持 `tools` 参数 | 只要能输出 JSON |
| 消息结构 | assistant.tool_calls + tool 消息 | 纯文本 + 【工具结果】前缀 |
| 适合 | Qwen2.5-7B / DeepSeek / GPT-4 级 | 0.5B~3B 本地小模型 |

提示协议的解析器做了容错：抓 ```json 代码块，也抓裸 JSON；单引号会尝试修复；
解析失败就当普通回复，不会把整个会话卡死。

### 审批为什么不放在前端做

审批状态在服务端 `AgentSession.pending` 里，是一个 `threading.Event`。
Agent 循环所在线程阻塞等待，HTTP 请求线程收到 `/api/agent/approve` 后 set 事件。
这样即使前端刷新页面、换一台设备点"允许"，循环也能继续——审批是会话级的，不是页面级的。

## 终端

三层：

1. **PTY**：POSIX 上 `pty.fork()` + `TIOCSWINSZ`，子进程以为自己在真终端里（`ls` 有颜色，`top` 能画界面）。
2. **环形缓冲**：每个会话保留最近 96KB 原始输出。断线重连时前端拉 `/api/term/buffer` 整体重建，
   不丢历史；页面刚打开时 shell 已经吐出的那几行也能补回来。
3. **VT 解析**（`js/vt.js`，独立模块）：字符网格 + SGR 状态机 + 光标控制 + 宽字符占两格。
   渲染时按样式合并 run，减少 `<span>` 数量。

不支持：滚动区域（CSI r）、鼠标上报、字符集切换。所以 `vim`/`htop` 会画歪，
`bash`/`git`/`make`/`python`/日志没问题。这是有意的取舍——真需要全屏 TUI 时，
用 SSH 或者以后加 xterm.js 作为可选渲染器。

宽字符处理很关键：中文文件名在 `ls` 里如果按 1 格算，整行会错位。这里对
CJK / 韩文 / 全角 / 常用 emoji 做了双宽处理，第二个格子存空字符占位。

## 沙箱

```
path → 展开 ~ 和环境变量 → resolve() → 必须落在 roots 之一内部（含子目录）
                                   → 否则 403
```

- `roots` 默认 `["~"]`，设置页可以加（例如 `/sdcard`、`/data`）。
- 删除不真删，移动到 `~/.jiaozi/trash/时间戳-文件名`。
- 上传走 base64 JSON（不写 multipart 解析器），单文件上限可配，默认 64MB。

这不是安全边界，只是**防手滑**。真正的隔离要靠容器/用户权限。

## 性能

目标：树莓派 4 / 4G 内存上能用。

- 后端零依赖，常驻内存约 30MB（不含模型）。
- 前端无框架、无构建，首屏 8 个文件，总共约 120KB 未压缩。
- SSE 事件很小（终端按 64KB 块切分），局域网延迟可忽略。
- 窗口用 `contain: layout paint` 隔离重排；拖拽用 transform 期间不触发全局布局。
- 终端渲染用 rAF 节流 + 150ms 兜底定时器（后台标签页 rAF 会停）。

## 已知失败模式

| 现象 | 原因 | 处理 |
|---|---|---|
| 模型一直转圈 | 端点不通 / 被系统代理劫持 | 本机与局域网地址会**绕过代理**直连；云端地址才走代理 |
| 小模型反复调用同一个工具 | 上下文里没看清结果 | 降 `max_steps`，或换 3B 以上模型 |
| 终端中文错位 | 用了非等宽字体 | 装 JetBrains Mono / Noto Mono |
| 板子上页面卡 | 无 GPU，backdrop-filter 太重 | 深色主题 + 减少窗口数量；可在 CSS 里关掉毛玻璃 |
| 安卓后台被杀 | 系统省电策略 | `termux-wake-lock`，并把 Termux 加入电池白名单 |

## 实测踩到的坑

下面每一条都是测试真跑出来的，不是设计时想到的。留在这里，因为它们是这个架构的真实成本。

**1. SSE 用 `Content-Length` 会挂住**
一开始想给流式响应算长度，结果浏览器永远等不到"结束"。改成 chunked transfer 才对——
流式响应本来就没有确定的结尾。

**2. 系统代理会劫持 127.0.0.1**
本机 Ollama 请求莫名 502，抓包才发现走的是公司的 HTTP 代理。`urllib` 默认读环境变量，
所以对 `localhost / 127.0.0.1 / 192.168.* / 10.*` 一律换成空 `ProxyHandler({})` 直连。
这个坑在国内办公网络里几乎必踩。

**3. 终端按键会串位（`echo` 变成 `ecoh`）**
每个按键独立 `fetch`，HTTP/1.1 下并发请求落在不同 TCP 连接上，到达顺序没有保证。
UI 测试里一次敲 19 个字符，服务端日志显示同一秒进了 **18 个并行请求**。
修法是前端做单通道队列：同一时刻只允许一个请求在途，期间的按键合并成一批再发。
副作用是请求数从 18 降到 2，对开发板是白赚的。

**4. 新终端一片空白**
管道模式的读取是"攒到换行才发"，而 shell 的提示符 `bash-5.3$ ` **不带换行**——
所以刚打开终端什么都没有，用户以为没启动。桌面测试没发现，因为测试紧跟着就敲了命令，
换行把提示符一起冲出来了。改成按块读、拿到就发、用增量解码器处理被切开的 UTF-8。

**5. 手机上文件名整个消失**
文件管理器侧栏固定 176px，390px 屏幕下把 `1fr` 的名称列压成 0 宽，只剩图标和时间。
测试原本只断言"列表有内容"，行数是对的，所以看不出来——是看截图看出来的。
窄屏改成顶部一排可横滑的快捷入口 + 只保留"名称/修改时间"两列，并把"文件名可见"
写成了带真实宽度测量的断言。

**6. 手机首屏是个聊天框**
AI 面板窄屏下是全屏的，默认展开就把桌面整个盖住。第一眼看到的不是"人机共用的桌面"，
而是"又一个聊天 App"——把产品最核心的东西藏没了。改成窄屏默认进桌面，
并在面板右上角给一个带"桌面"字样的出口。

**7. 刷新页面就刷屏报错**
浏览器关标签会让 `socketserver` 抛 `ConnectionResetError` 堆栈。开发板上这些日志会把
存储写满。重写 `handle_error` 静默掉断连类异常——断连是正常现象，不是故障。

**8. 后台标签页 rAF 不触发，终端不刷新**
SSE 事件到了、屏幕模型也更新了，但 `requestAnimationFrame` 在无合成环境里不跑。
加了一层 150ms 兜底定时器：`dirty` 还没清就直接画。

## AI 的手脚：图像生成为什么放在后端

`image_gen` 是 13 个工具里唯一"往外要东西"的：它调一个外部的文生图模型，
然后把结果**写进沙箱目录**，把路径交回给模型。

三个决定值得记下来：

**1. 不做成聊天窗口里的 base64 图片。**
如果把图片直接塞进消息气泡，它只存在于前端内存里——刷新就没了，别的程序也拿不到。
落到磁盘之后，同一张图可以：被文件管理器看到、被 `ui_open` 打开、被 `shell_run` 拿去 `scp` 上传、
被另一个视觉模型读回来。机器人没有浏览器，这一步是必须的。

**2. 复用 `llm` 的配置，但可以单独覆盖。**
大多数 OpenAI 兼容网关同时提供文本和图像端点，所以 `image.base_url`、`image.api_key`
留空就回落到 `llm`。本机跑 Ollama + 云端跑图像这种组合也能配。

**3. 前端要让人"看见"，不是让人读 JSON。**
工具结果是 `{"ok":true,"files":[...]}`，直接展示等于什么都没说。
所以 `step-card` 在检测到 `image_gen` 时会把 `files` 解析出来渲染成缩略图，点开进图片查看器。
图片查看器本身也支持直接打开一个**目录**——AI 经常把存图文件夹甩过来，这时当相册看才是对的。

这台机器上真实的端到端耗时：一句话 → AI 规划 → 两次工具调用 → 两张 832×1248 PNG，
**约 75 秒**，其中 90% 是图像模型自己的推理时间。

## 第二轮实测踩到的坑（接上真模型之后）

**9. Windows 上两个进程能同时监听同一个端口**
`SO_REUSEADDR` 在 Windows 上的语义和 Unix 完全不同：它允许第二个进程绑定一个**已经在监听**的端口。
于是"改完代码重启"其实启动了一个新进程，旧进程还活着，两个一起抢 accept——
请求随机落到旧代码上，表现为"改了没用"。最坑的是没有任何报错。
Python 的 `HTTPServer` 默认 `allow_reuse_address = 1`，正好踩中。
修法：Windows 上关掉 `SO_REUSEADDR`、改用 `SO_EXCLUSIVEADDRUSE`，并给端口占用一个人话错误提示。

**10. 脱敏后的 API Key 被原样提交回来，把真 Key 覆盖成星号**
`public_view()` 把 `api_key` 变成 `********` 返回给前端，前端又把它填进输入框的 `value`。
用户点一次"保存"，真实密钥就被八个星号替换，之后所有请求 401——而且界面上看起来一切正常。
两道防线：前端 `value` 留空只用 placeholder 提示"已设置"；后端 `save()` 里把空值和纯星号一律当作"不修改"。

**11. 一条 prompt 里写"第一张…第二张…"，模型画了张分屏**
想省一次调用，让 AI 传 `n=2` 并在一句话里描述两个场景。结果模型把两个场景**画进同一张画布**，
左右各一半，两张图长得一模一样。
这不是 API 的 bug，是提示词的问题：`n` 的语义是"同一画面的变体"，不是"不同场景"。
改回一次调用只描述一个画面、要几张就调几次，画质立刻正常。

**12. 白名单漏了一个键，配置静默丢失**
`/api/config` 有一层 `allowed` 字段白名单。加图像功能时忘了把 `image` 加进去，
于是设置界面里改图像参数、点保存、提示"已保存"——实际什么都没存。
是冒烟测试里"关闭图像后应该拒绝生成"这条断言把它抓出来的：开关关了还在花钱。
新增配置段时，**白名单和 DEFAULTS 必须同时改**。
